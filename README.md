## What I think makes this different

Most portfolios show that the author can get a query to run. These are the
things I would want to see if I were hiring:

**Three bugs I found in my own work, documented rather than quietly fixed.**

1. `NTILE` segment sizes were **non-deterministic** — three runs of the same
   query on the same data gave 1,006 / 1,003 / 1,029 customers, because ties in
   a non-total `ORDER BY` get placed arbitrarily under parallel execution. I
   noticed because the dashboard disagreed with the README.
   ([details](01-sql-retail-warehouse/README.md#caveats-and-limitations))
2. A price-typo filter was applied to revenue but **not to refunds**, producing
   customers with negative six-figure lifetime value who looked like ordinary
   low-value customers.
   ([details](01-sql-retail-warehouse/data_quality/FINDINGS.md))
3. A docstring claimed a sample-size shortcut was anti-conservative. It is
   conservative — `p(1−p)` is concave. A test caught it.
   ([details](tests/test_experiment.py))

**Results that argue against me.** The optimisation study reports that **two of
three rewrites stop paying at scale**, and that one of them produces a plan
identical to the version it was supposed to improve. The churn model's top
decile lift is 1.50x, which looks weak until you note the ceiling at a 57% base
rate is 1.74x — so the write-up explains the ceiling instead of hiding the
number.

**Claims that are executable.** `tests/test_parity.py` asserts the hand-written
SQL and the dbt project agree to the naira. `tests/test_experiment.py` validates
every hand-rolled statistic against statsmodels and scipy. Nothing in a README
says "I de-duplicated the data" without a test proving it.

**Decisions, with their costs.** Returns are reported separately rather than
netted off silently; price outliers are flagged, not overwritten; orphaned
orders keep their revenue but leave the per-customer averages. Each choice is
stated once, in one place, with what it gives up.

## Reproducibility

| | |
|---|---|
| **Data** | Synthetic, generated by [`src/generate_warehouse.py`](src/generate_warehouse.py) with a fixed seed. `make data` reproduces it byte for byte — there is a test asserting that. It carries eight deliberately planted data quality faults, [documented here](01-sql-retail-warehouse/data_quality/FINDINGS.md). |
| **Dependencies** | Pinned in `requirements.txt`. |
| **Tests** | `make test` — pytest across the generator, the staging layer, the dbt parity check and the statistics module. |
| **CI** | Every push runs lint, the full test suite, and a cold `make all` on a clean runner, so "it works on my machine" is not available to me. |

**Why synthetic data.** Every project runs the moment you clone the repo, with
no credentials and no 2 GB download, and the faults are known so the cleaning
decisions can be checked against ground truth. The cost is that no *business*
finding here describes a real company, and I say so at the top of each project.
Project 2 ships a working client for a real public API —
[run one command](02-python-pageviews/README.md) and its analysis is about real
data.
