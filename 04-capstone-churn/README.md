# Project 4 — Capstone: churn prediction and a winback experiment

**Question:** project 1 found 930 customers worth 17.8% of all-time revenue who
have been silent for a year. Can we predict who is about to go quiet, and does
contacting them actually work?

**Answer.** Yes to the first, out of time, at ROC AUC 0.745 — and the second
question cannot be answered by any model, only by an experiment. So the
deliverable is a **pre-registered test design**, and the most useful thing the
project produced is the power calculation that **invalidated my own first
design**: targeting the 930 at-risk customers could only ever have detected a
7-percentage-point lift, so a real, valuable effect would have come back as "not
significant". Widening the target to the model-scored active base and splitting
50/50 instead of 70/30 fixes it.

**→ Read [`reports/decision-memo.md`](reports/decision-memo.md) first.** It is
the one-page version written for a Head of Growth. Everything below is how it
was built.

## The three things that make this more than a model

### 1. The label is drawn in time, and the leak is the whole difficulty

The hard part of a churn model is not the model. It is drawing the line between
*what we knew then* and *what happened next* without letting the second leak into
the first.

```
observation cutoff  = last order date in the data, minus 90 days
feature window      = everything strictly BEFORE the cutoff
label window        = the 90 days AFTER the cutoff, with an upper bound
churned             = no order placed in the label window
eligible            = ordered at least once in the 180 days BEFORE the cutoff
```

That last line is the one that matters most. My first version defined eligibility
as "ever ordered", and scored **99.1% churned** — because a base accumulated over
two years is mostly people who left long ago. A model trained on that learns
"almost everyone churns", is right 99% of the time, and is useless. The business
question is not "has this customer ever lapsed", it is "of the customers active
today, which will go quiet". Restricting to the recently-active base gives a
**57.4% churn rate** and a real classification problem.

The label window also needs an upper bound. Without one it runs to the end of the
data, which is correct *only* when the cutoff happens to sit exactly 90 days from
the end — and silently becomes a 270-day window for the earlier training
snapshot, making the two sets of labels incomparable. That bug was in the first
version of the SQL.

### 2. Validation is out of time, and the optimism is reported

Most churn write-ups report a random train/test split. That leaks: the rows are
not independent draws, they are one photograph of one customer base at one
moment.

So this trains on a snapshot from **2 April 2025** (n=2,088, 68.6% churn) and
tests on a different one from **29 September 2025** (n=2,754, 57.4% churn). Note
the churn rates differ by 11 points — the base genuinely got healthier as the
business grew, and a random split would have hidden that drift entirely.

| Validation scheme | ROC AUC |
|---|---|
| Random 70/30 split within the test snapshot | 0.743 |
| 5-fold CV within the test snapshot | 0.740 (± 0.015) |
| **Honest out-of-time** | **0.745** |
| Optimism from in-snapshot validation | **−0.005** |

The interesting result is that the optimism is **essentially zero**. I expected
the in-snapshot numbers to flatter themselves and they did not, which is evidence
that the features genuinely respect the cutoff. Had the gap been large, it would
have pointed straight at a leak. Reporting the comparison is the point: the
number is only reassuring *because* it was checked.

| Model | ROC AUC | PR AUC | Brier |
|---|---|---|---|
| Baseline (predict base rate) | 0.500 | 0.574 | 0.257 |
| **Logistic regression** | **0.745** | 0.772 | **0.207** |
| Gradient boosting | 0.729 | 0.773 | 0.215 |

Logistic regression wins. With 23 features and 2,088 training rows, the boosted
model has nothing to find that the linear one misses, and it costs
interpretability and calibration. Reaching for the fancier model here would have
been a worse decision, not a more sophisticated one.

### 3. The model's own diagnostics catch it misleading me

**Lift has a ceiling.** Top-decile lift is 1.50x, which looks poor next to the
5x–10x in published churn case studies. But at a 57.4% base rate a *perfect*
ranking can only reach 1/0.574 = **1.74x**, so 1.50x is **86% of the best any
model could possibly do**. Those published figures come from problems with 2–5%
churn. Comparing raw lift across base rates is meaningless, and the script now
reports the ceiling alongside the number.

**Two coefficients have the wrong sign.** The model says more lifetime orders
*increase* churn risk. The raw data says the opposite, and clearly:

| Lifetime orders | 1 | 2 | 3 | 4–5 | 6–8 | 9+ |
|---|---|---|---|---|---|---|
| Churn rate | 74% | 66% | 56% | 49% | 44% | **33%** |

The cause is collinearity: `orders_total` correlates 0.92 with `active_months`
and 0.90 with `revenue_total`, so the fit splits shared signal between them
arbitrarily and one lands negative. The script detects this automatically by
comparing each fitted coefficient against the feature's raw top-versus-bottom
tercile churn rate, and prints a `SIGN FLIPS` warning naming the features whose
coefficients must not be read as effects.

This is the diagnostic I am proudest of, because the failure it catches is one I
would otherwise have committed in the memo. A ranking model and an explanatory
model are different things, and a logistic regression on correlated features is
only the first.

## Honest limitations

- **The experiment has not been run.** This is a design and a pre-registered
  analysis plan, not a result. The "if the test works" figures in the memo are
  the hypothesised outcome, labelled as such everywhere they appear.
- **The 6% baseline reactivation rate is an assumption**, and it is the largest
  uncertainty in the whole design. The control arm measures it directly, which is
  a second reason not to drop the holdback.
- **Calibration is slightly over-confident at the top.** The riskiest decile is
  predicted at 0.918 and observes 0.859. Fine for ranking; it would need
  isotonic or Platt recalibration before any probability was used in a
  cost-per-contact calculation.
- **No causal claim about any feature.** See the sign-flip section. The model
  ranks; it does not explain.
- **Synthetic data.** The generator is deterministic and documented in
  `../src/generate_warehouse.py`. The method is the deliverable, not the
  business conclusion.
- **One model family, lightly tuned.** No hyperparameter search beyond sensible
  defaults. With 2,088 training rows a search would mostly fit noise, and the
  out-of-time gap is the number I would want to protect.

## What I would do next

1. **Run the test.** Everything else is secondary.
2. **Add a survival model** (Cox or Kaplan–Meier). Binary churn-in-90-days throws
   away the timing information, and "when" is more actionable than "whether" for
   scheduling a lifecycle email.
3. **Recalibrate before using probabilities as costs.** Ranking is enough for a
   send list; expected-value targeting needs calibrated probabilities.
4. **Prune the collinear features** and refit, to get a model whose coefficients
   can be read. Keep the full-feature model for ranking, since dropping features
   would cost AUC for no ranking benefit. Two models for two jobs.
5. **Design the geo holdout** for the paid-social question from project 1, which
   randomisation cannot reach.
